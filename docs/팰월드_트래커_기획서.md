# 팰월드 4거점 트래커 — 기획서 v3

> **v3 핵심: 별도 앱이 아니라 기존 체크리스트의 "생성기"로 합친다.**
>
> | | v1 (원안) | v3 (현재) |
> |---|---|---|
> | 배치 | 새 레포 | 기존 레포, 라우트 추가 |
> | 인증 | `ADMIN_TOKEN` + 쿠키 + middleware | 기존 **`CONTROL_KEY`** 그대로 |
> | 오버레이 | `/overlay` 새로 구현 | **기존 `/o/[id]` 재사용** (`id='pal'`) |
> | Realtime | `overlay_state` 새 테이블 + 구독 | **기존 `lists`/`items` 구독 그대로** |
> | 체크리스트 | 건설 중심 | **재료 파밍 → 제작 → 건설** |

---

## 1. 확정 스펙

| 항목 | 결정 |
|---|---|
| 스택 | 기존 레포 그대로 — Next.js 15 App Router + TypeScript + Supabase + Vercel |
| 배치 | 새 레포 아님. 같은 사이트, 다른 라우트 (`/control` 옆에 `/pal`) |
| 사용자 | 본인 1명 (방송 시청자는 읽기만) |
| 관리자 인증 | **`CONTROL_KEY`** 1개 — 체크리스트와 완전히 공유 |
| 진입 | `/pal?key=...` → Gate 가 localStorage 에 저장, 다음부터 `/pal` 만으로 입장 |
| 오버레이 | **신규 구현 없음.** 기존 `/o/pal` (= `lists.id = 'pal'`) |
| 핵심 흐름 | **보유 재료 입력 → 부족량 계산 → "지금 뭘 파밍할지" 를 순서대로 제시** |
| 출력 | 계산 결과를 `lists`/`items` 에 sync → 오버레이가 알아서 갱신 |

## 2. 두 프로젝트를 합치는 방법

### 2-1. 왜 합쳐지는가

트래커가 최종적으로 만들어내는 건 **"다음에 할 일 목록"** 이다. 그건 체크리스트 앱이
이미 하는 일이다. 그래서 트래커를 독립 앱으로 두지 않고, **체크리스트 한 개를 자동으로
채워주는 생성기**로 만든다.

```
[팰월드 트래커 /pal]                     [기존 체크리스트]
 재고 입력 ─→ BOM 계산 ─→ 할 일 N개 ──sync──→ lists(id='pal') + items
                                                      │
                                                      ↓ (기존 Realtime)
                                              /o/pal  오버레이
```

`lists.id` 는 `text primary key` 라서 `'pal'` 이라는 고정 id 를 넣을 수 있다. 그러면
오버레이 URL 이 `/o/pal` 이 되는데, **이건 새 라우트가 아니라 기존 `/o/[id]` 가
처리하는 URL 이다.** scale·hideDone·sortProgress 같은 기존 쿼리 옵션도 전부 그대로 먹는다.

### 2-2. 덕분에 안 만들어도 되는 것

| 원안에 있던 것 | v3 |
|---|---|
| `pal_overlay_state` 테이블 + RLS + publication | 불필요 |
| `/o/pal` 전용 page/layout/css | 불필요 — 기존 `/o/[id]` 가 처리 |
| 오버레이 payload 스키마·렌더링·토스트·진행률 바 | 불필요 — 이미 구현돼 있음 |
| Realtime 구독 배선 | 불필요 — 이미 구현돼 있음 |
| OBS 재설정 | 기존 소스 복제 후 URL 만 `/o/pal` 로 |

구현 단계가 하나 통째로 빠진다.

### 2-3. 합치기 위해 기존 스키마에 더할 것 (2줄)

```sql
-- 이 목록은 사람이 만든 것인가, 트래커가 만든 것인가
alter table public.lists add column if not exists source text not null default 'manual';

-- 트래커가 생성한 항목의 안정적인 식별자 (uuid 는 매 sync 마다 바뀌면 안 되므로)
alter table public.items add column if not exists ref text;
create unique index if not exists items_list_ref_idx
  on public.items (list_id, ref) where ref is not null;
```

`default 'manual'` 과 nullable `ref` 라서 **기존 체크리스트 동작은 하나도 안 바뀐다.**
부분 인덱스(`where ref is not null`)를 쓰는 이유는 손으로 만든 항목들이 `ref = null` 로
여러 개 존재할 수 있기 때문이다.

### 2-4. sync 는 한 트랜잭션 안에서 diff upsert

```sql
create or replace function public.pal_sync_list(p_items jsonb)
returns void language plpgsql security definer set search_path = public as $$
begin
  insert into lists (id, title, source) values ('pal', '팰월드 4거점', 'pal')
    on conflict (id) do update set title = excluded.title, source = 'pal';

  -- 없어진 항목 제거
  delete from items
   where list_id = 'pal'
     and ref is not null
     and ref not in (select x->>'ref' from jsonb_array_elements(p_items) x);

  -- 있는 건 갱신, 없는 건 삽입
  insert into items (list_id, ref, label, done, position)
  select 'pal', x->>'ref', x->>'label', (x->>'done')::boolean, (x->>'position')::int
    from jsonb_array_elements(p_items) x
  on conflict (list_id, ref) where ref is not null
  do update set label = excluded.label, done = excluded.done, position = excluded.position;
end;
$$;

revoke execute on function public.pal_sync_list(jsonb) from anon, authenticated;
```

> ⚠ **전체 삭제 후 재삽입 방식으로 만들지 말 것.** Realtime 이 삭제 이벤트를 먼저
> 흘려보내서 방송 중 오버레이가 한 번 빈 화면으로 깜빡인다. 반드시 diff upsert 다.

### 2-5. `/control` 에서의 취급

`source = 'pal'` 인 목록은 `/control` 에 **읽기 전용**으로 뜬다.

- 배지 "🤖 트래커가 관리" + `/pal` 로 가는 링크
- 항목 추가/수정/삭제/순서변경 버튼 숨김 — 다음 sync 때 어차피 덮어써진다
- 체크박스도 비활성 — 완료 여부는 재고에서 나온다
- 목록 자체의 삭제·이름변경은 허용 (`sort` 로 위치는 조정 가능)

`/api/mutate` 에도 방어를 넣는다: `rename_list` 를 제외한 mutation 이 `source='pal'`
목록을 대상으로 오면 400 으로 거절.

## 3. 라우트 배치와 인증

### 3-1. 라우트

```
/control        🔒 체크리스트 컨트롤 (팰월드 목록도 읽기 전용으로 함께 표시)
/o/[id]         🌐 오버레이 — 체크리스트도 팰월드(/o/pal)도 전부 여기
/api/mutate     🔒 체크리스트 쓰기

/pal            🔒 팰월드 트래커 (신규 — 탭 UI)
/api/pal/mutate 🔒 팰월드 쓰기 + sync (신규)
```

**새로 만드는 라우트는 `/pal` 과 `/api/pal/mutate` 둘뿐이다.**

### 3-2. 인증 통일 — `CONTROL_KEY`

**`ADMIN_TOKEN` 은 만들지 않는다.** 환경변수는 기존 4개에서 늘어나지 않는다.

| 기존 자산 | 팰월드에서의 역할 |
|---|---|
| `lib/auth.ts` → `keyMatches(candidate)` | 서버 컴포넌트에서 `?key=` 검증 (상수 시간 비교) |
| `lib/auth.ts` → `requireKey(req)` | `/api/pal/mutate` 에서 `x-control-key` 헤더 검증 |
| `lib/env.ts` → `CONTROL_ENV` / `missingEnv()` | 환경변수 누락 시 `SetupNotice` 표시 |
| `app/control/Gate.tsx` | 키 입력 폼 + localStorage 자동 재진입 |

`Gate.tsx` 는 리다이렉트 경로가 `/control` 로 하드코딩돼 있으므로
**`components/Gate.tsx` 로 옮기고 `redirectTo` / `title` prop 을 받게 일반화**한다.
`localStorage` 키는 양쪽 모두 기존 이름 `control_key` 를 쓴다 — 그래야 `/control` 에
한 번 들어간 브라우저가 `/pal` 도 키 입력 없이 바로 열린다.

```
/pal            → key 없음        → <Gate redirectTo="/pal" />  → 저장된 키로 자동 재진입
/pal?key=틀림   → keyMatches 실패 → <Gate invalid />            → 저장된 키 삭제 후 재입력
/pal?key=맞음   → 트래커 렌더
```

> 쿠키·`middleware.ts` 는 쓰지 않는다. 기존 사이트가 의도적으로 쿼리스트링+localStorage
> 방식을 택했고, 미들웨어를 끼우면 `/o/*` 오버레이까지 걸려서 방송 화면이 깨진다.

### 3-3. `/pal` 을 단일 라우트로 두는 이유

`?key=` 인증은 페이지를 이동할 때마다 키를 URL 로 물고 다녀야 한다. 링크 하나만
빠뜨려도 Gate 로 튕긴다. 그래서 관리자 화면은 **`/pal` 단일 라우트 + 클라이언트 탭**
으로 만든다 (`/control` 과 같은 구조). 거점 선택도 `/pal/bases/2` 가 아니라 서브탭이다.

## 4. 보안 설계

```
[관리자 화면]  /api/pal/mutate + service_role 키 (서버에서만) → 모든 쓰기
[오버레이]     anon 키 + RLS → lists/items 읽기 (기존 정책 그대로)
```

- **`pal_*` 테이블은 anon 전면 차단** — 정책을 하나도 만들지 않는다. 재고 수치·레시피·
  거점 구성이 방송에 새지 않는다.
- 공개되는 건 **sync 로 내보낸 `items.label` 뿐**이다. 이건 어차피 화면에 띄우려고
  만든 문장이므로 노출돼도 무방하다.
- `service_role` 키는 `app/api/` 아래에서만 `adminClient()` 로 사용

> sync 할 때 label 에 무엇을 넣는지가 곧 "무엇을 방송에 공개할지"다. 재고 총량을
> 숨기고 싶으면 `"발화 기관 2,140/6,598"` 대신 `"발화 기관 32%"` 로 내보내면 된다.
> 이걸 `/pal` 설정에서 토글로 둔다.

## 5. 체크리스트 모델 — 파밍 → 제작 → 건설

이 앱의 본질은 건축물 체크리스트가 아니라 **"지금 뭘 캐고 뭘 사냥해야 하는지"** 를
알려주는 것이다. 설계도 16-2 기준 최하위 재료만 8만 개가 넘고, 16-5 는 진짜 병목이
건설이 아니라 **속성별 팰 사냥 루트**라고 못박고 있다. 그래서 3단계로 세운다.

```
[1단계 파밍]  최하위 재료를 모은다      ← 여기서 시작. 대부분의 시간이 여기 들어간다
     ↓ 재고가 차면 자동으로 해금
[2단계 제작]  중간재를 만든다            ← 1차 가공 → 제련 → 조립 → 최종 부품
     ↓
[3단계 건설]  건축물을 짓는다
```

### 5-1. 세 단계의 "완료" 판정이 서로 다르다

| 단계 | 완료 판정 | 왜 |
|---|---|---|
| 파밍 | **체크박스 없음.** `보유량 ≥ 필요량` 이면 자동 완료 | 재료는 22,038개 단위라 체크박스가 무의미하다. 재고 입력이 곧 체크다 |
| 제작 | 체크박스 없음. 재고 반영으로 판정 | 만들면 산출물 재고가 오르고 재료 재고가 준다 |
| 건설 | **체크박스 (`pal_checklist.done`)** | 지었다/안 지었다가 이분법이고 DB 가 알 방법이 없다 |

사용자가 실제로 손대는 입력은 **재고 숫자**와 **건설 체크박스** 둘뿐이다.

### 5-2. 파밍 작업(farm task)의 단위

재료를 하나하나 나열하면 60줄이 넘어 방송에 못 쓴다. **획득처(`pal_farm_sources`)로
묶어서** 작업 단위를 만든다. 설계도 16-2 의 A~E 분류가 그대로 획득처가 된다.

| 획득처 | 방식 | 묶이는 재료 | 비고 |
|---|---|---|---|
| 물질 생성기 (거점②) | 자동 | 금속 광석·석탄·돌·순수한 석영·솔라이트 광석·유황·목재·크로마이트·헥소 석영·팰지움 파편·단단한 목재·코랄리움 광석 | 생성기 5대, **품목 고정**. 가동 중 품목 변경 시 속도 급락 |
| 고압형 원유 추출기 (거점④) | 자동 | 원유 | |
| 가축 목장 (거점③) | 자동 | 양털 | |
| 화염 팰 사냥 | 수동 | 발화 기관 | ⚠ 최대 병목 (6,598) |
| 번개 팰 사냥 | 수동 | 발전 기관 | |
| 기름 드롭 팰 사냥 | 수동 | 고급 팰 기름 | 그린모스 등 |
| 독 팰 사냥 | 수동 | 독샘 | |
| 물 팰 사냥 | 수동 | 수생 팰의 점액 | |
| 얼음 팰 사냥 | 수동 | 빙결 기관 | |
| 팰 해체 | 수동 | 뼈·가죽 | |
| 세계수 원정 | 수동 | 팰키사이트 광석·세계수의 성수·신비한 목재 | 성수는 필드 보스 확정 드롭 |
| 유물·던전 | 수동 | 고대 문명의 코어·고대 문명의 부품 | |

`/pal` 파밍 탭에서 한 줄은 이렇게 보인다:

```
🔥 화염 팰 사냥          발화 기관   2,140 / 6,598   (32%)   ██████░░░░░░░░░░░░░░
⛏ 물질 생성기 (거점②)   금속 광석  4,200 / 22,038  (19%)   ███░░░░░░░░░░░░░░░░░
                         석탄       1,100 / 19,244  ( 5%)   █░░░░░░░░░░░░░░░░░░░
```

### 5-3. 자동 획득처는 "시설 건설"이 선행이다

금속 광석 22,038개는 물질 생성기가 있어야 자동으로 모인다. 생성기가 아직 없으면
파밍 작업을 띄우는 게 아니라 **"고대 문명 물질 생성기 1대 건설"** 을 최상단에 올려야
한다 (설계도 16-5 의 1번 조언). `pal_farm_sources.requires_structure` 로 표현한다.

```
requires_structure 가 있고 그 건축물이 아직 미완성  → 파밍 작업 대신 그 건설 작업을 노출
requires_structure 가 없거나 이미 완성              → 파밍 작업 그대로 노출
```

### 5-4. 체크리스트는 저장물이 아니라 파생물이다

`pal_checklist` 에 저장하는 건 **건설 단계의 `done` 플래그뿐**이다. 나머지는 재고가
바뀔 때마다 계산 엔진이 다시 만들어낸다.

```
목표 건축물 목록 (미완성인 것만)
  → expand() 로 BOM 전개, 재고 선차감
  → 최하위 재료별 부족량
  → 획득처로 묶기
  → farmScore 로 정렬
  → 상위 N개 → pal_sync_list() → lists/items → 오버레이
```

## 6. DB 스키마

> ⚠ **접두사 `pal_` 필수.** 기존 스키마에 이미 `public.items`(체크리스트 항목)와
> `public.lists` 가 있다. 접두사 없이 `items` 를 만들면 기존 체크리스트가 깨진다.
> 파일은 `supabase/schema-pal.sql` 로 분리한다. 기존 `schema.sql` 에는 2-3 의 두 줄
> (`lists.source`, `items.ref`)만 추가한다.
> 기존 파일과 같이 **여러 번 실행해도 안전하게**(`if not exists` / `drop policy if exists`) 쓴다.

```sql
-- ── 획득처 (파밍 작업의 단위) ────────────────────────
create table if not exists public.pal_farm_sources (
  id        text primary key,          -- 'hunt_fire'
  name      text not null,             -- '화염 팰 사냥'
  method    text not null,             -- auto | manual
  place     text,                      -- '거점② 물질 생성기' / '화산 지대'
  icon      text,                      -- 오버레이용 이모지 '🔥'
  sort      int  not null default 0,
  note      text,
  -- 이 시설이 있어야 자동 획득이 시작된다. 미완성이면 파밍 대신 건설을 먼저 띄운다.
  requires_structure text
);

-- ── 게임 데이터 (수정 가능) ──────────────────────────
```

## 7. 계산 엔진

### 7-1. BOM 전개

```ts
// 재고를 먼저 차감하고 내려가는 게 핵심.
// 컴퓨터를 300개 갖고 있으면 그만큼은 하위 전개를 하지 않는다.
function expand(itemId, qty, stock, out, seen = new Set()) {
  if (seen.has(itemId)) throw new Error(`순환 참조: ${itemId}`);

  const have = Math.min(stock[itemId] ?? 0, qty);
  stock[itemId] -= have;
  const need = qty - have;
  if (need <= 0) return;

  const recipe = recipes[itemId];
  if (!recipe) { out[itemId] = (out[itemId] ?? 0) + need; return; }   // 최하위 재료

  const batches = Math.ceil(need / recipe.yield);
  out[`craft:${itemId}`] = (out[`craft:${itemId}`] ?? 0) + batches;   // 제작 지시
  for (const ing of recipe.inputs) {
    expand(ing.id, ing.qty * batches, stock, out, new Set([...seen, itemId]));
  }
}
```

주의: `stock`은 **복사본**을 써야 한다. 원본을 깎으면 재계산할 때마다 값이 어긋난다.

### 7-2. 파밍 작업 만들기

```ts
// 1) 미완성 건축물 전체를 전개해 최하위 재료 부족량을 얻는다
// 2) 부족 재료를 획득처별로 묶는다
// 3) 각 재료가 "얼마나 많은 걸 막고 있는지"(blockedBy)를 함께 센다
function farmTasks(structures, stock, done) {
  const targets = structures.filter(s => !done.has(s.id));
  const shortage = {};          // itemId -> 부족량
  const blockedBy = {};         // itemId -> 이 재료 때문에 못 짓는 구조물의 unlock_score 합

  for (const s of targets) {
    const out = {};
    const copy = { ...stock };                       // ⚠ 반드시 복사본
    for (const c of s.costs) expand(c.itemId, c.qty * s.count, copy, out);
    for (const [id, n] of Object.entries(out)) {
      if (id.startsWith('craft:')) continue;
      shortage[id]  = (shortage[id]  ?? 0) + n;
      blockedBy[id] = (blockedBy[id] ?? 0) + s.unlock_score;
    }
  }

  const bySource = groupBy(Object.keys(shortage), id => items[id].source_id);
  return Object.entries(bySource).map(([srcId, itemIds]) => ({
    source: sources[srcId],
    items: itemIds.map(id => ({
      id, name: items[id].name,
      have: stock[id] ?? 0,
      need: (stock[id] ?? 0) + shortage[id],
      short: shortage[id],
    })),
    score: farmScore(sources[srcId], itemIds, shortage, blockedBy),
  })).sort((a, b) => b.score - a.score);
}
```

## 8. 우선순위 알고리즘

### 8-1. 파밍 작업 점수

```
farmScore(획득처) = Σ blockedBy(재료) / 10        // 이 획득처가 막고 있는 상위 건축물의 무게
                  + (method === 'manual' ? 4 : 0) // 수동이 진짜 병목 (설계도 16-5)
                  + 미달성률(0~10)                // 1 - 보유/필요, 낮게 채워진 것부터
                  + (자동인데 시설 미완성 ? 999 : 0)
```

마지막 항이 핵심이다. 자동 획득처인데 `requires_structure` 가 아직 안 지어졌으면
**그 시설 건설을 최상단으로 끌어올린다.** 물질 생성기 1대만 지으면 광물 12종이
한꺼번에 풀리기 때문에, 다른 어떤 작업보다 먼저다.

### 8-2. 건설 작업 점수

```
score(구조물) = unlock_score × 3
              + base.weight × 2
              + 완성근접도(0~10)      // 부족 재료가 적을수록 높음
              - 선행미충족 ? 999 : 0  // 못 짓는 건 뒤로
```

### 8-3. 두 목록을 합쳐 sync 한다

오버레이에 나가는 최종 목록은 파밍과 건설을 섞은 단일 목록이다.

```
1. 자동 획득처의 미완성 선행 시설 (물질 생성기 등)   ← 있으면 무조건 최상단
2. 재료가 이미 충분해서 지금 바로 지을 수 있는 건축물 ← 즉시 성과, 진행률이 오른다
3. farmScore 상위 파밍 작업                          ← 평소엔 여기가 대부분
+ 최근 완료 3개 (done=true)                          ← 성취감. hideDone=1 로 끌 수 있다
```

이 목록을 `pal_sync_list()` 에 넘긴다. `ref` 는 `farm:hunt_fire`, `build:ancient_furnace`
같은 안정적인 문자열을 쓴다.

**unlock_score 기준값 (초기 시드)**
| 건축물 | 점수 | 이유 |
|---|---|---|
| 고대 문명 화로 | 10 | 팰키사이트·솔라이트 주괴 → 사실상 모든 상위 건축의 선행 |
| 고대 문명 물질 생성기 | 9 | 광물 12종 자동화 |
| 고대 문명 발전기 | 8 | 전력 시설 전부의 선행 |
| 고도 문명 작업 공장 | 6 | 컴퓨터·AI 코어 제작 |
| 고대 문명 작업대 | 5 | 팰키사이트 장비 전용 |
| 고대 문명 배합기 | 4 | 작업 팰 양산 |
| 고대 문명 재배기 | 3 | 식량 |
| 침대·온천·감시대 | 1 | 편의 |

**base.weight**: ② 자원 3 / ① 메인 2.5 / ④ 배합·원유 2 / ③ 농사 1.5

## 9. 화면 구성

`/pal` 내부 탭 (하위 라우트 아님):

| 탭 | 내용 |
|---|---|
| **할 일** | 8-3 합산 목록 + 전체 진행률 + "오버레이로 내보내기" 상태. 앱을 열면 여기가 먼저 |
| **재고** | 보유 재료 입력. 획득처별 그룹, 절대값/증분 입력 |
| **파밍** | 획득처별 전체 목록 + 재료별 보유/필요/부족 진행률 바 |
| 제작 | 제작 순서 트리 (1차 가공 → 제련 → 조립 → 최종 부품), 각 항목에 필요/보유/부족 |
| 거점 | 거점 ①~④ 서브탭: 건축물 체크리스트(체크박스) + 팰 배치표 |
| 데이터 | 레시피·건축물 비용·`unlock_score`·획득처 직접 수정 |

`/` 는 지금처럼 `/control` 로 리다이렉트한다. 팰월드는 URL 을 직접 친다.

### 9-1. 재고 탭이 제일 중요하다

이 앱에서 반복적으로 하는 행동은 **재고 숫자 입력** 하나다. 그래서:

- 획득처별로 묶어서 보여준다 — 사냥 갔다 오면 그 그룹만 고치면 된다
- 절대값 입력과 **증분 입력(`+250`)** 을 둘 다 지원한다. 파밍 후엔 증분이 훨씬 편하다
- 입력 즉시 낙관적 업데이트 → `/api/pal/mutate` → 재계산 → `pal_sync_list()` → 오버레이
- 부족량이 0이 된 재료는 흐리게 처리해 시야에서 빼준다

### 9-2. 오버레이에 나가는 문장

```
🔥 화염 팰 사냥 — 발화 기관 2,140/6,598 (32%)
⚡ 번개 팰 사냥 — 발전 기관 0/3,234
🌳 세계수 원정 — 성수 1,200/2,670
🏗 물질 생성기 2대 건설 — 재료 충족
✅ 유황 완료
```

label 한 줄이 곧 오버레이 한 줄이다. 총량을 방송에 감추고 싶으면 `pal_settings` 의
토글로 `"발화 기관 32%"` 형태로 바꿔 내보낸다. 렌더링·진행률·토스트·`scale` 은
기존 오버레이가 이미 처리한다.
